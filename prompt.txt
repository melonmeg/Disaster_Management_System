## 4. MySQL integration and data integrity

Use the existing schema and sample-data files. Verify that the backend models and database operations match the actual tables, column names, keys, data types, and constraints.

Implement reliable database connectivity and configuration using environment variables. Provide an `.env.example` with placeholders and never commit actual credentials.

Ensure that:
- Primary keys and foreign keys are respected.
- Invalid references and duplicate operations are handled appropriately.
- Incident, dispatch, unit, responder, and resource relationships remain consistent.
- Resource allocations cannot exceed available stock.
- Related database writes use transactions when necessary.
- Errors are handled without exposing credentials or internal details.
- Existing sample records and identifiers are preserved.

Do not unnecessarily recreate the database or regenerate the existing SQL files. Warn me and obtain approval before destructive database operations or migrations that could lose data.

## 5. Advanced SQL requirements

The college DBMS rubric gives significant marks to advanced database concepts. Implement meaningful, executable SQL demonstrations using the existing schema and realistic emergency-response scenarios.

Prioritize the features explicitly required by the available rubric:

- CRUD operations.
- Multi-table joins.
- Nested and correlated subqueries.
- Aggregate functions, `GROUP BY`, and `HAVING`.
- Common Table Expressions (CTEs).
- A meaningful recursive query where supported and appropriate.
- Stored procedures.
- Stored functions.
- Triggers.
- Transactions, commit, and rollback.
- Useful views and indexes.

Build examples around:
- Listing incidents by severity, status, and location.
- Retrieving units and responders associated with incidents.
- Summarizing dispatches per incident.
- Finding available units and resources.
- Allocating and returning resources.
- Identifying incidents involving multiple patients.
- Tracking unresolved incidents and response activity.
- Calculating useful operational summaries.

Use syntax compatible with the actual MySQL version. Avoid adding artificial features merely to increase the number of scripts.

Organize SQL demonstrations into clear files if suitable files do not already exist. Include short comments identifying each task and enough explanation to demonstrate the feature during a viva.

Test important operations with valid and invalid inputs. Ensure transactions roll back correctly when a related operation fails.

## 6. Backend APIs

Implement or complete the APIs required by the application, reusing existing conventions.

### Authentication
- Registration if required.
- Login and logout/session handling.
- Current authenticated user.
- Token refresh or invalidation where appropriate.

### Organizations
- List, view, create, update, and delete operations as permitted.

### Responders
- List and view responders.
- Create and update responder records.
- Assign or reassign responders to units.
- Retrieve responders assigned to a unit.
- Update responder availability.

### Units
- List and view units.
- Create and update units.
- Retrieve unit availability and current assignments.

### Incidents
- List, filter, and view incidents.
- Create incidents and update status.
- Retrieve incident details, dispatches, and patients.
- Resolve incidents when permitted by business rules.

### Dispatches
- Create dispatches connecting incidents and units.
- Update dispatch status.
- Retrieve dispatch history.
- Validate that referenced incidents and units exist.
- Prevent invalid operations and enforce appropriate state transitions.

### Resources
- Retrieve resources and availability.
- Allocate resources to dispatches.
- Record returned quantities.
- Prevent negative stock and over-allocation.
- Keep stock and allocation records consistent.

### Patients
- Retrieve and manage patient records associated with incidents.
- Respect the existing composite primary key and foreign-key constraints.

### Calls and activity logs
Expose the necessary API endpoints for the frontend to retrieve calls and activity logs through the agreed architecture. Coordinate the response formats and identifiers with my teammate rather than implementing duplicate MongoDB storage.

For all APIs:
- Validate inputs.
- Use appropriate HTTP methods and status codes.
- Return consistent error responses.
- Handle missing records, invalid references, and permission failures.
- Use pagination and filtering where useful.
- Document endpoint paths, request bodies, response formats, and permissions.

Keep the API implementation modular and maintainable without unnecessary abstractions.

## 7. Authentication and authorization

The college rubric requires authentication, at least two roles, and role-based access control, including database-level enforcement as specified by the assignment.

Implement a practical role model, such as `admin` and `responder`, adapted to the actual requirements.

Requirements:
- Secure password hashing.
- Appropriate session or token handling.
- Protected backend routes.
- Server-side permission checks on every protected operation.
- Clear permissions for each role.
- MySQL users and privileges or another appropriate database-level enforcement design that satisfies the rubric.
- Least-privilege database accounts.
- Secure environment configuration.

Do not rely on frontend restrictions alone. Distinguish application-level authorization from MySQL privileges and demonstrate both where required.

Test that each role can perform permitted actions and is blocked from unauthorized operations. Never hardcode credentials or expose password hashes and secrets.
